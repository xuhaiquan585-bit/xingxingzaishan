## 3. 角色、状态与记录流程

### 3.1 角色

| 角色 | 权限依据与边界 |
| --- | --- |
| 无凭证访客 | 可看公开产品介绍；不能凭编号读取顾客记录或获得访问凭证 |
| 持有效扫码/分享凭证的查看者 | 在记录状态允许时查看对应记录；持有凭证不等于拥有记录、修改或管理权 |
| 已验证身份的首次记录者 | 结合有效星贴凭证和未激活状态提交记录；身份以服务端会话为准 |
| 记录所有者/共创发起人 | 通过服务端身份及归属校验访问自己的记录、管理未封存共创；不能修改已封存正文 |
| 共创参与者 | 持有效凭证并满足登录/手机号验证规则后，按共创限制参与 |
| 管理员/质检人员 | 通过各自角色授权执行管理或质检；知道编号不等于拥有管理权限 |

### 3.2 生命周期（U/C）

| 状态 | 允许行为 | 不允许行为 |
| --- | --- | --- |
| 未激活 | 凭有效入口查看填写状态；完成身份验证、上传及预览确认后提交 | 按明码抢占；重复绑定；无身份提交 |
| 共创中 | 按归属和参与权限留言、管理有效留言、由发起人最终封存 | 匿名读取共创内容；非发起人封存或删除他人留言 |
| 已封存/已激活 | 凭有效查看资格回看记录；异步更新真实存证状态 | 重新填写、改写照片/正文/已封存留言、替换成另一人的记录 |
| 隐藏或不可访问 | 按对应状态阻止公共访问，由授权人员处理 | 通过分享、媒体、旧接口绕过限制 |

这里的文字状态用于需求描述；代码可以使用 `unactivated`、`co_creating`、`activated` 等映射。发行状态、印刷状态、记录生命周期和存证状态必须分开，不得拿一个字段替代全部状态。

**FLOW-001：**正常主流程为：扫描有效星贴 → 必要的身份验证 → 添加照片和文字 → 预览并明确确认提交后不可修改 → 保存 → 回看。已激活星贴再次扫描进入查看，不重新填写。

**FLOW-002：**主记录当前为一张照片及最多 200 字的文字；文字可为空的既有接口规则继续保留。改变必填性、计数方式或容量，须同步前后端校验与用户提示，不借文案改动偷偷变更。

**FLOW-003：**同一星贴只能成功绑定一次最终记录。并发提交、重试或重复点击不得生成第二份记录、覆盖第一份内容，或产生重复的有效业务扣费。

**FLOW-004：**H5 手机号验证、小程序微信身份与手机号绑定、归属判断必须由服务端可信会话处理，不能相信客户端提供的手机号、所有者标记或记录 ID。

**FLOW-005：**“我的记录”只能返回当前用户有权访问的记录。手机号变更、账号找回不得仅凭星贴编号转移所有权；具体找回步骤与身份校验的调整须单独评审。

**FLOW-006：**上传失败、超限或提交失败时不得把旧图当成新图提交，也不得显示虚假的保存成功；允许用户明确重试，不破坏已保存记录。

**CO-001：**保留“直接保存/邀请共创”既有能力。共创留言每条最多 50 字，每个已验证手机号在同一记录下最多 1 条有效留言，每条共创记录最多 12 条有效留言。

**CO-002：**共创发起人可在封存前删除留言并最终封存；删除后不占有效条数。参与者不能自行封存；第一版不增加参与者修改留言能力。主照片和主留言代表发起人，不额外要求发起人重复留言。

**CO-003：**共创发起及留言阶段不生成最终上链结果；最终封存包含当时保留的全部有效内容。封存后不得继续写入或删除已封存留言。

## 4. 安全、随机令牌与隐私边界

### 4.1 三种概念必须分开

- **展示编号/内部 ID：**用于贴纸印字、发货、售后和内部关联，可以连续；不是密码或公共访问凭证。
- **随机访问凭证：**扫码或分享入口携带的不可预测凭证，只用于其授权范围；不是账号登录凭证。
- **账号身份与角色：**服务端认证后确认的用户身份、归属或管理员权限；不能由任意 URL 参数代替。

### 4.2 防枚举硬性要求（U/C）

**SEC-001：**公共访问不得仅凭二维码明码/连续编号获取顾客记录。即使编号真实存在，也必须校验有效访问凭证或独立的所有者/管理员权限。

**SEC-002：**随机令牌校验失败后不得回退到编号查询。把明码放进 `t`、`key`、`qr` 或其他参数，改参数名称、编码形式或请求通道，均不能产生访问权。

**SEC-003：**分享必须使用不可预测且作用域正确的凭证。分享信息接口本身也必须校验凭证或归属，不得允许匿名或无权用户凭编号换取令牌、记录正文或二维码图片。

**SEC-004：**公共记录读取、分享、下载、记录媒体代理、二维码 PNG、H5、小程序及可公开访问的静态资源必须遵守相同边界。不能只保护页面而让图片或旧接口成为旁路；适用的 JSON 与 PostgreSQL 实现都需覆盖。

**SEC-005：**公共读取凭证不自动授予激活、编辑、归属变更、共创管理、下载正式印刷文件等权限。写操作另外校验身份、归属、生命周期及资源授权。

**SEC-006：**令牌使用密码学安全随机源；承接当前 16 随机字节的生成强度，不能改用序号、时间戳、可逆编码或可预测派生值代替。令牌必须唯一；格式改变前核对全部消费者及历史实物码。

**SEC-007：**令牌只在受控扫码、授权分享或必要印刷链路中使用，不在普通公开 DTO、CSV、报错、分析材料或日志中额外暴露。管理员印刷文件内含可扫描凭证，整个文件按敏感生产资料处理。

**SEC-008：**不得为了兼容旧明码链接而恢复公共编号兜底。历史明码分享链接应失效；若实物存量中存在明码入口，先制定受控迁移/售后方案，不静默保留漏洞。已有合法随机令牌的实物贴纸应保持可用，不擅自全量轮换令牌。

**SEC-009：**“我的记录”或管理端允许使用内部 ID 定位对象，但必须校验当前身份和对象归属/角色。登录任意账号不能靠其他人的 ID 越权访问。

**SEC-010：**无有效凭证的查询不得泄露记录是否存在、所有者或内容。错误响应保持必要且一致；限流只作为辅助，不能替代授权校验。

**SEC-011：**后台与质检令牌必须绑定操作员当前账号状态及认证版本。账号停用、重新启用、角色或用户名变更、密码变更后，变更前签发的令牌不得继续使用或在重新启用后复活；受保护请求不能只校验令牌签名和其中自带的角色。当前登录管理员不得通过普通停用接口停用自己。

### 4.3 隐私与可见范围（U/C）

**PRIV-001：**当前产品允许持有有效实物二维码或分享链接的人查看已封存且可见的记录，不宣传“只有本人/情侣双方可看”。提交前必须让用户理解可见范围，避免上传敏感隐私内容。

**PRIV-002：**有效分享链接可能被转发。防枚举不等于私密访问；本版不新增密码分享、收件人白名单、限次或可撤销分享。若需要这些能力，单独确定产品与令牌生命周期方案。

**PRIV-003：**公开数据采用字段白名单，不暴露完整手机号、OpenID、会话凭证、对象键、供应商密钥、后台操作标识或错误堆栈。用户内容按文本安全渲染，不能直接拼接成可执行 HTML。

**PRIV-004：**隐藏/禁用等限制必须检查相关公共入口。新授权应被阻止，但已经下载的副本和仍在有效期内的外部签名 URL 不能承诺即时收回；具体时效以实现和验收为准。

**PRIV-005：**生产不得用 mock 身份、mock 内容安全结果或 mock 存证成功掩盖缺失配置；密钥、访问令牌、完整手机号和客户原始记录不得写入 Git、普通日志或共同知识库。支付及供应商业务日志采用必要字段白名单，不持久化付款人 OpenID、设备、客户端 IP 或完整回调载荷来代替正式业务字段。

## 5. 图片、存储、备份与恢复

### 5.1 图片存储规格（C，当前实现基线）

| 环节 | 规则 |
| --- | --- |
| 原始上传 | 当前服务端上限 5 MiB；格式、文件内容、维度及像素量须服务端校验 |
| 主图 | 规范化 JPEG，最长边不超过 1600 px，最大 800 KiB，即 819200 字节 |
| 列表缩略图 | 最长边不超过 640 px，最大 120 KiB |
| 画质 | 纠正方向、保持比例；按既有质量/尺寸策略压缩，不保证任意原图细节完全无损 |
| 不满足约束 | 明确拒绝并提示，不绕过上限、不静默存入不合格对象 |

**DATA-001：**800 KiB 是正式存储主图的体积上限，不是要求用户事先把原图压到 800 KiB，也不是服务器进程的内存配额。历史图片不得因新规格被批量重新压缩或删改。

**DATA-002：**生产顾客图片使用私有 OSS 及受控访问；对象键是内部引用，不是永久公开地址。主图与缩略图成功保存后才释放本次缓冲；失败须可明确恢复，不丢失已确认数据。

**DATA-003：**上传凭证、对象归属和记录绑定必须服务端校验，不能把另一个用户的图片或任意对象 URL 绑定到自己的记录。不得仅凭文件后缀信任图片。

**DATA-004：**前台列表用缩略图、详情用主图；显示/下载失败应可重取授权地址。签名过期不应被误判为图片永久丢失。

### 5.2 备份边界（U/C）

**BKP-001：**数据库备份不等于图片备份。恢复范围须包含权威数据库、顾客图片字节、记录清单及索引、必要的正式印刷资料与恢复说明，明确哪些已覆盖、哪些尚缺。

**BKP-002：**顾客图片应有与主存储故障域隔离的备份方案；“同一 Bucket 不同目录”不自动算独立备份。第二 Bucket 的地域、账号/权限隔离、保留期、复制和恢复方式未确定前，不宣称已实现跨地域或第三方容灾。

**BKP-003：**历史缓冲、孤立对象、旧本地图片和旧库不得按年龄直接删除。须核对实际引用、备份及恢复可行性，形成候选清单并取得删除授权。

**BKP-004：**备份完成至少核验对象存在、大小和完整性，恢复能力须有独立演练证据。手工备份成功不能当作定时备份已启用；RPO、RTO、周期、保留期和告警责任见 P-002。

**BKP-005：**“长期可回看”依赖服务、数据库和图片可用性，区块链哈希不能代替原始内容备份。不得承诺供应商退出后仍无条件永久查看。

## 6. 数据权威与区块链存证

### 6.1 数据权威（C）

**DB-001：**已经完成 PostgreSQL 权威切换的身份、二维码、记录生命周期、记录读取及相关生产领域，禁止在失败时静默回退到历史 JSON。代码回滚不能通过读取旧 JSON 隐藏 PostgreSQL 中的新业务数据。

**DB-002：**权威按业务领域确认，不能推断全库所有模块均已迁移。商品、订单、支付、管理员或内容配置等领域是否仍由 JSON 管理，按有效迁移合同和实际配置核对，不由本次文档整理自动切换。

**DB-003：**数据库结构/迁移、权威选择器、导入导出及回滚都属于高风险变更，先定范围、校验和、备份和恢复方案。生产数据库名字含 `staging` 不意味着它是可丢弃测试库。

### 6.2 存证语义（U/C）

**PROOF-001：**OSS 保存内容与封存清单，AVATA/文昌链保存必要的内容摘要等存证信息；不把照片和文字全文直接上链，不把产品作为 NFT 或投资产品宣传。

**PROOF-002：**最终清单覆盖对应照片内容摘要、文字及适用的共创、展示信息，采用稳定规则生成哈希。需保留清单版本及核验关系；不能只保存一个与实际内容无关的随机字符串充当证明。

**PROOF-003：**“生成内容哈希”“提交存证”“链上确认”是不同阶段。未确认不得显示“已完成区块链存证”；上传时间、记录保存时间与链上确认时间不得混为一谈。

**PROOF-004：**对外可表述为“完成区块链存证后，可用于核验记录内容是否与存证时一致”。不得表述成证明事件真实、证明上传以来每个时刻从未变化，或证明内容永久可用。

**PROOF-005：**异步任务、回调和重试必须验签/校验关联并保持幂等，不通过重建清单、重复上链或重复扣费掩盖失败。直接保存与最终封存的业务状态、待存证任务必须保持一致。

**PROOF-006：**顾客显示照片、文字、编号、时间、真实存证状态和可核验哈希；后台可查看授权范围内的运维信息。顾客不能看到内部对象键、operation_id、供应商错误原文及密钥。

**PROOF-007：**已封存内容不得通过归档重建、重试或后台操作悄悄重写。数据纠错、隐私处理、删除请求如何与保留的存证关系协调，需专项方案，见 P-005。

## 7. 标签设计、印刷与库存

**PRINT-001：**编辑画布、服务端预览和正式生产必须使用同一尺寸、字体、排版及二维码/编号组件约定。前端拖拽层不能用独立 CSS 排版结果冒充最终权威图。

**PRINT-002：**二维码编码内容为真实有效的随机凭证入口，印字为对应展示编号。二者对应关系不可错配；编号位置、居中、字号联动及间距由统一组件规则处理，不在各端分别估算。

**PRINT-003：**二维码保持正方形、高对比和规定静区。编辑框含静区，不能为放大黑色码纹而裁掉静区。画布与预览保持相同物理比例，缩放只影响屏幕显示，不扩大实际留白。

**PRINT-004：**文字、分割线颜色等已支持的模板属性应能保存并在预览和正式文件中一致输出。校验失败须指出具体元素、字段和约束，并给出可操作信息；不能只返回“模板不符合要求”。

**PRINT-005：**模板草稿可编辑；发布版本只读，修改需新草稿版本。正式任务绑定固定模板版本，不被后续编辑影响。

**PRINT-006：**正式印刷使用服务端输出的 600 DPI PNG/ZIP，像素尺寸按毫米换算。当前 30×80 mm 成品对应约 709×1890 px；历史 20×80 mm 示例不是当前商品规格。预览截图及普通二维码 PNG 不能代替正式生产文件。

**PRINT-007：**单次任务承接 1 至 500 张上限；同一码不能进入两个有效印刷任务。同一正式任务重复下载必须返回同一文件，不重新生成另一份不同成品。

**PRINT-008：**生成前取消可按事务释放预留；正式文件确认后不得解绑、改绑或重新预留。报废按具体编号及原因登记，补印使用新二维码和新任务，不复用已打印或报废码。

**PRINT-009：**正式文件放私有 OSS，管理员鉴权下载并留审计。CSV 不含访问令牌、手机号或对象键；二维码图片本身仍是敏感资料，不能因 CSV 干净而公开整个 ZIP。

**PRINT-010：**正式销售前验证成品尺寸、裁切、扫码和油性笔书写。屏幕预览通过不等于实体打样通过；演示图上覆盖二维码的处理严禁进入可售实物印刷文件。

**FUL-001：**当前少量销售允许人工管理印刷库存到订单的对应，不宣称自动闭环。每天记录实际发货日期、平台订单关联、SKU、数量和具体星贴 ID。

**FUL-002：**连续且无缺号时可记录起止编号和总数；存在跳号、报废、补发时必须记录具体清单，数量与实物一致，防止重复发货。订单与个人信息限授权人员使用，不把随机令牌抄进普通发货表。

## 8. 前台展示、店铺和详情页

**UX-001：**保持扫码业务页流程稳定，文案可在不改变规则前提下改善；按钮动作、登录回跳、上传状态、分享与“我的记录”入口不得因美化丢失。

**UX-002：**手机端文字可读、按钮可点、长文本不溢出；原始顾客照片默认完整展示，不因装饰性裁切遗漏记录内容。H5 与小程序可以视觉不同，但权限和业务规则一致。

**UX-003：**首页以“记在星上”和已确认主标题、星贴实物/场景为核心；当前网站购买入口只保留微信店铺方向，不自行新增抖音跳转。抖音仍是销售推广平台之一，二者不冲突。

**UX-004：**“了解星贴”到网站首页、自建小程序商品页、外部微信店铺为三种不同目标；不能把它们都称为已打通店铺。普通浏览器、微信内 H5、小程序的跳转需分别验证，不承诺任意环境一键直达。

**UX-005：**原生分享可用时按有效分享数据调用，不支持时复制有效链接；不能将分享降级成自动下载或意外打开下载页。分享成功不能绕过第 4 节。

## 9. 管理、销售与支付边界

**OPS-001：**管理员、质检人员按角色访问；普通用户不得调用批量发行、隐藏、导出、印刷、存证重试或订单管理接口。批量不可逆操作须明确对象、数量及确认步骤，并保留不含秘密的审计。

**OPS-002：**小程序订单与微信支付已有代码不等于店铺生产支付已验收。启用或调整支付需核对商户配置、金额、订单归属、回调真实性与幂等；生产禁止 mock 支付成功。

**OPS-003：**外部平台店铺订单与自建小程序订单分开识别，不把人工发货登记冒充自动支付/库存同步。当前不扩大为完整电商后台。

## 10. 发布、回滚与执行边界

**REL-001：**讨论、写文档、改代码、提交、推送、预检、生产部署是不同阶段。没有用户对相应外部操作的授权，不得自动跨阶段执行。

**REL-002：**生产部署固定目标 commit、tree、适用迁移校验和及回滚目标。预检通过不等于已经部署；HTTP 200 不等于扫码、图片、分享、印刷和安全验收都通过。

**REL-003：**执行前核验近期可恢复备份、环境和数据权威、真实生产端点、秘密保护及受影响业务状态；部署后核对实际版本、健康和受影响功能。不得为了让预检通过而关闭安全门禁。

**REL-004：**生产长命令通过已审核的仓库 runner 或可校验脚本交付，进行语法检查及必要的完整性核验，避免 Markdown 转义和链接污染。聊天中不给未经验证的大段维护脚本。

**REL-005：**真实 OSS、短信、支付、区块链、生产数据库和破坏性操作只在授权范围内使用；优先通过本地静态检查、合成数据和隔离环境收敛问题，不拿真实顾客记录做枚举实验。

**REL-006：**回滚保留数据权威、已封存记录及正式印刷事实。不得以应用回滚为名恢复更弱的访问控制、让已打印码重新可分配，或丢失 PostgreSQL 新写入；修复后的防枚举同样属于回滚验收条件。

**REL-007：**保护用户未提交修改。只提交本次授权范围的文件；测试结果必须注明实际执行范围，不能用历史 PASS 代替当前受影响合同的验证。

## 13. 变更控制

### 13.1 标准流程

1. **提出变更：**列明当前规则编号、旧行为/文案、新要求、原因和是否降低安全或兼容性。
2. **分析影响：**检查 H5、小程序、后台、数据、存量实物码、印刷文件、备份、成本及宣传口径的受影响范围；无需扩大到无关模块。
3. **取得确认：**由用户批准需求变化。不得把“讨论可行性”“写文档”或“测试通过”当作部署授权。
4. **同步基线：**更新本文、关联专项文档、变更记录与验收目标。保留被替代条目的编号和历史，不删除安全要求以迁就错误实现。
5. **实施验证：**按风险执行受影响测试，用合成数据验证拒绝和允许两类路径；发现同类旁路进行有界排查。
6. **交付发布：**报告需求版本、实现提交、测试范围和未闭合项；推送与生产部署按授权分别进行。

### 13.2 变更类型

- **规则不变的修复：**例如恢复 SEC 防枚举，应引用原编号并修复实现/测试，不把漏洞登记成兼容功能；仍遵守必要的风险沟通和发布授权。
- **新增或改变规则：**例如开放视频、允许封存后修改、改变共享隐私、扩大图片上限或更换数据权威，必须先确认再改基线。
- **配置或纯文案调整：**既有范围内的模板内容/颜色等无需每次升规范版本；若改变商品规格、价格基线、可见范围或承诺，则不再是纯文案。
- **紧急安全处置：**可优先提出限流、暂停入口或其他止损方案，但影响线上用户的动作仍须授权。不能以紧急修复为由悄悄执行数据迁移或撤销全部实物码。
