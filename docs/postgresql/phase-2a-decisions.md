# PostgreSQL Phase 2A Decisions

## Scope

Phase 2A-1 created a reviewable SQL schema and a side-effect-free configuration parser. Phase 2A-2 adds explicit pool/transaction helpers and a guarded runner without routing application traffic away from the JSON database.

## Driver and migration tooling

- The recommended runtime driver is `pg` because the target architecture needs explicit transactions, row locks, parameterized SQL, and a small connection pool without an ORM abstraction.
- `pg` 8.22.0 is installed as the only direct PostgreSQL dependency in Phase 2A-2.
- The schema remains plain SQL so it can be reviewed independently from a JavaScript migration framework.
- Phase 2A-2 uses a small migration runner built on `pg`, with canonical SHA-256 verification, ordered files, `schema_migrations`, and a session advisory lock. The checksum normalizes CRLF bytes to LF while preserving every other byte, and Git pins migration SQL files to LF.
- Do not introduce Knex, Prisma, Sequelize, TypeORM, or another ORM in this migration program. The repository contracts and SQL constraints remain the source of persistence behavior.

## PostgreSQL target

- Minimum target: PostgreSQL 15.
- Application objects live in the dedicated `app` schema and are always schema-qualified.
- The initial migration does not create a database, role, extension, or seed row.
- Production access will use TLS, least-privilege roles, statement timeouts, and a bounded connection pool in a later phase.

## Identifier strategy

- Existing account IDs, QR IDs, product IDs, order IDs, order numbers, batch IDs, and valid numeric identity IDs are preserved.
- Surrogate numeric keys use `GENERATED BY DEFAULT AS IDENTITY` so an importer can preserve valid historical numbers and then reset sequences above the imported maximum.
- UUID primary keys are generated by application/importer code and supplied explicitly. The database schema intentionally has no UUID default because Phase 2A-1 must not require `pgcrypto` or another extension.
- Historical identifiers that do not safely fit the target primary key retain a scoped or global `legacy_id` as defined by the importer specification.

## Status and ownership boundaries

- `users` stores login identities. It is not the business principal; business ownership always points to `accounts`.
- `qr_codes.lifecycle_status` only represents `unactivated`, `co_creating`, or `activated`.
- Payment, proof, archive, quality-check, import, and outbox states have independent CHECK constraints and must never be added to QR lifecycle status.
- Phone and OpenID columns on records and orders are immutable historical or provider snapshots, not ownership keys.

## Deletion and history

- Accounts, identities, QR codes, records, orders, payments, proof records, audit events, and import history use restrictive foreign keys.
- Only catalog configuration children (`product_images` and `product_scene_tags`) use `ON DELETE CASCADE`.
- Soft deletion is retained for co-creation comments. Historical comments are not physically removed as a side effect of account changes.

## Migration execution policy

- `001_init_schema.sql` is forward-only SQL and contains no transaction commands. The runner wraps its SQL and matching `schema_migrations` insert in one transaction.
- There is no down migration. Rollback before cutover means dropping a disposable schema/database using an explicitly reviewed operator procedure, not running destructive SQL from the application repository.
- The SQL has static and unit coverage but must not be described as production-ready until it has run successfully against a disposable PostgreSQL 15+ instance and its constraints have been exercised.
- The Phase 2A-2 runner rejects production targets. A dedicated least-privilege migration role and temporary PostgreSQL validation are still required before any shared environment is used.

## Runtime boundary

- `src/server/database/config.js` only parses and redacts configuration and performs no import-time validation.
- `connection.js` imports `pg` but creates no pool until `createPostgresPool()` is called.
- `transaction.js` and `healthCheck.js` receive a pool explicitly. They are not imported by current application startup.
- Existing application startup and `dbService` continue to use JSON.
- A future connection module must be created only after the driver choice is approved and must not silently activate PostgreSQL based on partial environment variables.
