# PostgreSQL Schema v1

## 1. Global conventions

- PostgreSQL timestamps use `timestamptz` and are written in UTC.
- Money is stored as integer cents in `bigint`; floating point is prohibited.
- Existing stable business IDs remain text and are not renumbered.
- New internal child-row IDs use `bigint generated by default as identity` or UUID.
- Historical numeric IDs are imported into identity columns when safe, followed by sequence reset.
- Historical non-numeric or locally scoped IDs use a new surrogate primary key plus `legacy_id text`.
- Phone, OpenID, and UnionID are strings, never numeric values.
- SHA-256 values use `char(64)` with a lowercase hexadecimal check after normalization.
- Provider transaction hashes and operation IDs use bounded `varchar` or `text`, not the SHA-256 type.
- Business states use `CHECK` constraints. PostgreSQL enum types are not the default.
- JSONB is limited to immutable snapshots or structured provider/audit metadata with an explicit whitelist.
- All mutable domain tables have `created_at` and `updated_at` unless they are immutable event logs.
- Foreign-key columns are indexed when used in ownership, list, or status queries.
- Core business rows use `ON DELETE RESTRICT`. Cascading deletion is allowed only for non-business child configuration such as product image ordering.

## 2. QR and record lifecycle

`qr_codes.lifecycle_status` is the high-level scan lifecycle and accepts `unactivated`, `co_creating`, and `activated`.

```text
unactivated -> activated
unactivated -> co_creating -> activated
```

- Direct save creates one `records` row, seals it, and changes the QR to `activated` in one transaction.
- Starting co-creation creates one unsealed `records` row and one active `co_creations` row, then changes the QR to `co_creating`.
- Finalize locks the QR, record, and co-creation; verifies ownership; seals the existing record; finalizes co-creation; and changes the QR to `activated`.
- A record is unsealed when `sealed_at IS NULL`. It does not have a second lifecycle column that competes with the QR lifecycle.
- Proof, archive, quality-check, payment, and outbox state never extend `lifecycle_status`.

## 5. Table designs

### `accounts`

| Column | Type | Rules |
|---|---|---|
| `id` | `varchar(32)` | PK; preserve `ACC...` |
| `status` | `varchar(24)` | NOT NULL; CHECK active/disabled/closed |
| `display_name` | `varchar(120)` | NOT NULL default empty |
| `avatar_url` | `text` | NOT NULL default empty; sensitive URL |
| `created_from` | `varchar(32)` | CHECK web_phone/miniapp_openid/migration/admin_repair |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL |

Indexes: status; created_at. `app.account_id_seq` allocates the numeric suffix
for new `ACC` IDs without scanning or locking the accounts table. Migration
`005` initializes its next value above the largest imported suffix and blocks
nonconforming historical IDs. The staging importer realigns the sequence after
loading accounts for fresh migration-first environments. Accounts are not
physically deleted by normal business flows.

### `users`

`users` stores login identities, not business ownership. Business ownership always follows `account_id` to `accounts`.

| Column | Type | Rules |
|---|---|---|
| `id` | `bigint identity` | PK; preserve numeric legacy IDs when valid |
| `legacy_id` | `text` | UNIQUE; required when source ID cannot be represented safely by `id` |
| `account_id` | `varchar(32)` | NOT NULL FK accounts, ON DELETE RESTRICT |
| `phone` | `varchar(32)` | Nullable; sensitive |
| `openid`, `unionid` | `varchar(160)` | Nullable; sensitive |
| `source` | `varchar(32)` | NOT NULL CHECK web/miniapp/web+miniapp/migration |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL |

Indexes: account_id; partial unique normalized phone; partial unique openid; optional unionid index after audit. Application normalization must match importer normalization exactly.

### `operators`

Identity PK plus `legacy_id`; username unique; password_hash text; role CHECK admin/qc; name; enabled; created/updated timestamps. No password value is exposed through repositories. Historical `checked_by`/`created_by` strings may remain snapshots when an operator FK cannot be proven.

### `qr_batches`

Text PK preserving batch ID; name; brand_name; note; disclosure text/default; nullable creator FK plus creator snapshot; timestamps. Index created_at. `print_batches` is deferred unless a production-copy audit finds authoritative print batch entities; `print_batch_id` remains a nullable legacy reference meanwhile.

### `qr_codes`

Text PK; issue_status CHECK; lifecycle_status CHECK; hidden; nullable batch FK; nullable print_batch_id; QR image snapshot; access_token; created_at/updated_at. Indexes: partial unique access_token, batch_id, issue/lifecycle status, hidden, created_at.

### `records`

`qr_id` text PK/FK; account_id FK; content text; image URL snapshot; image object key; image SHA-256; phone snapshot; sealed_at; brand disclosure fields; created_at/updated_at. Indexes: account_id + sealed_at descending; sealed_at; image_object_key. A row may be unsealed only while its QR is `co_creating`.

### `co_creations`

UUID PK; qr_id unique FK; owner_account_id FK; owner_phone_snapshot; status CHECK active/finalized/closed; started_at/finalized_at; created_at/updated_at. Indexes: owner account + status; status + started_at.

### `co_creation_comments`

UUID PK; co_creation_id FK; account_id FK; `legacy_comment_id text`;
`source_position integer NOT NULL`; `legacy_duplicate boolean NOT NULL DEFAULT
false`; phone snapshot; author_name; content; status CHECK kept/deleted;
created_at/deleted_at. Constraints: unique co-creation + legacy ID, unique
co-creation + source position, non-negative source position, and partial unique
co-creation + account for effective comments whose `legacy_duplicate=false`.
The importer marks only the second and later kept historical comments for the
same account as legacy duplicates. They remain real, visible comments and keep
their source positions. New runtime writes must use the default false value;
the Repository forces false and this flag is not a general bypass for the
one-effective-comment rule. Deleted
comments remain auditable, retain their original source positions, are never
renumbered, and are not cascaded with account deletion. Public reads exclude
deleted comments and order visible comments by `created_at DESC,
source_position ASC`; `legacy_duplicate` is never exposed in the DTO.

Migration `002_add_comment_source_position.sql` adds this field without a
default. It intentionally refuses to run when PostgreSQL already contains
comment rows because their original JSON order cannot be reconstructed from
database row order. Such staging databases must be recreated and imported
again from the verified JSON snapshot.

### `quality_check_logs`

Identity PK; legacy_id text; qr_id FK; nullable operator_id FK; checked_by_snapshot; result CHECK pass/bound/duplicate; checked_at. Indexes: qr_id + checked_at; checked_at; result. Event rows are immutable.

### `products`, `product_images`, `product_scene_tags`

Products preserve text ID and contain scalar catalog fields, integer-cent price, stock, product status/type CHECKs, shipping/after-sale text, sort order, and timestamps. `buy_type` accepts the current `miniapp_order` mode and the audited historical `copy_link` compatibility value; new runtime writes remain `miniapp_order`. Product images use identity PK, product FK, URL/object key, sort order. Scene tags use composite PK product_id + scene_key. Product child configuration may use ON DELETE CASCADE; orders retain immutable product snapshots.

### `orders`

Preserved text ID; order_no unique; account FK; nullable product FK; openid/phone snapshots; product_snapshot JSONB; quantity; unit and total cents; order/payment status CHECKs; payment method/mock marker; transaction snapshot; paid/shipped timestamps; receiver and address fields; logistics/refund/admin fields; timestamps. Indexes: account + created_at descending; order status + created_at; payment status; order_no; provider transaction value when non-empty. Receiver fields are restricted PII and excluded from general audit output.

### `payment_transactions` and `payment_events`

Transactions use UUID PK, order FK, provider, merchant order number, provider transaction ID, amount cents, status CHECK, paid_at, created_at/updated_at. Unique provider + provider transaction ID and provider + merchant order number enforce idempotency. Payment events use identity PK, nullable transaction/order FK, event type/status, sanitized JSONB metadata, stable payload hash, and created_at; events are immutable.

### `record_proofs`, `proof_attempts`, `record_archives`

Proofs use UUID PK, record QR FK, provider, status CHECK, unique operation ID,
manifest key/hash, `legacy_hash_snapshot`, transaction result, certificate
metadata, confirmed/callback timestamps, retry count, last error, and
timestamps. `manifest_hash` remains a strict lowercase SHA-256. A non-empty
historical value that was stored in both JSON hash aliases is preserved only
in `legacy_hash_snapshot`; the two columns are mutually exclusive. Candidate
reads may use that snapshot to reproduce the legacy public DTO, but new proof
writes must populate the canonical hash field and the Repository forces the
legacy snapshot column to null. Attempts use identity PK, proof
FK, attempt number, requested/result state, sanitized error, timestamps, and
unique proof + attempt number. Archives use record QR PK/FK, current/legacy
manifest keys, index key, status CHECK, last error, and timestamps.

### `miniapp_content`

Singleton smallint PK with CHECK `id = 1`; scalar content fields; slides and scene cards JSONB; updated_by operator FK/snapshot; updated_at. JSONB shape is validated at the service boundary and later may receive database checks if stable.

### `audit_events`

Bigint identity PK; actor_type; actor reference or hashed snapshot; action; entity_type; entity_id/hash; request method/path; result status; IP/UA policy-safe representation; duration; sanitized metadata JSONB; created_at. `actor_reference_hash` and `entity_reference_hash` are full normalized SHA-256 values (`char(64)` plus lowercase hexadecimal checks); short redacted report references remain separate migration-report fields. No full phone, OpenID, address, token, user text, image URL, or payment payload.

### `outbox_jobs`

UUID PK; job_type; aggregate_type/id; idempotency_key unique; payload JSONB whitelist; status CHECK pending/processing/succeeded/failed; attempt count; available_at; locked_at/locked_by; last_error; timestamps. Index pending jobs by status + available_at.

### `import_runs`, `import_anomalies`, `schema_migrations`

Import runs use UUID PK, source SHA-256 unique, source label without sensitive path details, mode, status, count/checksum summaries, started/completed timestamps. Anomalies use identity PK, import run FK, severity/category/entity type, hashed legacy reference, field, count, blocking flag, and sanitized detail. Schema migrations record version, checksum, and applied_at.

## 6. Sensitive data policy

- Phone, OpenID, UnionID, receiver name/phone/address, provider payloads, and signed URLs are sensitive.
- Production connections require TLS and least-privilege roles.
- Backups require encryption and restore testing.
- Payment and audit metadata use explicit whitelists; raw provider documents are not retained by default.
- Data retention and deletion policy must be approved before production cutover. Restricted PII is never included in shadow-diff or importer anomaly output.

## 7. Migration order

1. Infrastructure tables: `schema_migrations`, `import_runs`, `import_anomalies`.
2. Principals: `accounts`, `users`, `operators`.
3. Catalog/issuance: `qr_batches`, `products`, product children.
4. QR and content: `qr_codes`, `records`, `co_creations`, comments, QC logs.
5. Commerce: `orders`, payment transactions/events.
6. Integrity: proofs, attempts, archives.
7. Presentation/audit: miniapp content, audit events, outbox jobs.
8. Reset identity sequences and validate deferred constraints.
